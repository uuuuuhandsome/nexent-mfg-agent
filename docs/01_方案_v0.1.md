# 先进制造 · 标准符合性核查智能体（工作名：SpecGuard）

> 版本 v0.1 ｜ 用途：三人小队对齐目标、拆分工作、对齐赛题五条要求
> 场景可替换，但**「数值/单位可计算 + 标准条款对齐 + 判定可审计」**这个骨架建议保留

---

## 1. 一句话定义

把一份产品的**技术要求**（招标规范书参数表）和一份**检测报告**（实测值）喂进去，
自动对照适用的**国标/行标条款**，输出逐条符合性判定、证据链、不符合项整改建议。

**使用者**：制造业企业的投标/质检/合规工程师——投标前自查能不能满足技术规范书，避免废标。

---

## 2. 为什么这个场景能拿分

赛题五条要求，它能一次全占住：

| 赛题要求 | 本场景的对应设计 |
|---|---|
| 多模态异构数据统一识别 | 参数表（表格）+ 标准条文（长文本/嵌套表格）+ 扫描件检测报告（OCR/图片理解） |
| 低资源本体半自动构建 | 从标准文本抽取「指标—限值—试验方法」三元组，少量人工标注做种子 |
| MCP + Skills 双驱动 | 数值比较、单位换算必须走工具；判定流程固定 → 封装成 Skill |
| 跨文档多跳 + 可溯源 | 四跳链路，每跳落到「文档—页码—条款号/表格行」 |
| 基于 Nexent 可运行 | 知识库 + 智能体 + MCP 工具 + Skill，全部落在平台内 |

**核心洞察**：制造场景里 LLM 最不可靠的是「数值、单位、等级、区间判定」。
这正好是把工具（MCP）用起来的理由，而不是用提示词硬凑。
评委看到「模型不自己算，而是调 `numeric_compare` 工具算」——这就是编排深度。

## 3. 数据来源（全部公开）

| 来源 | 网址 | 拿什么 | 备注 |
|---|---|---|---|
| 国家标准全文公开系统 | openstd.samr.gov.cn | GB 标准全文 | 部分可在线阅读/下载 |
| 全国标准信息公共服务平台 | std.samr.gov.cn | 标准目录、状态、代替关系 | 判断条款是否现行有效 |
| 中国政府采购网 | ccgp.gov.cn | 招标文件/技术规范书 | 真实多模态文档，含扫描件 |
| CMA/CNAS 检测机构公开样张 | 各机构官网 | 检测报告样例 | 注意脱敏 |
| 企业产品样本 | 厂商官网 PDF | 产品参数表 | 用于构造对照 |

**起步建议**：先锁定 **1 个产品品类**（例如「低压成套开关设备」或「工业用离心泵」），
只做这一个品类的 15~20 份文档，把链路跑穿，再横向扩展。
**不要一上来做全品类**——这是最常见的失控点。

## 4. 本体 Schema（草案）

### 实体

| 实体 | 关键属性 |
|---|---|
| `Product` | 品类、型号、制造商 |
| `Requirement` | 参数名、限值、单位、方向（≥/≤/区间）、来源（招标/标准） |
| `Standard` | 标准号、名称、状态（现行/废止）、实施日期 |
| `Clause` | 条款号、层级（章-节-条-款-表）、正文、引用关系 |
| `TestItem` | 试验项目、试验方法（引用的条款）、实测值、单位、报告编号 |
| `Verdict` | 符合 / 不符合 / 无法判定、理由、置信度 |
| `Evidence` | 文档 ID、页码、定位（条款号 / 表格行 / 图区域） |

### 关系

```
Product --requires--> Requirement
Requirement --governed_by--> Clause
Standard --contains--> Clause
Standard --supersedes--> Standard        # 废止/代替关系，关键！
Requirement --tested_by--> TestItem
TestItem --yields--> Verdict
Verdict --evidenced_by--> Evidence
```

### 关键约束（这些才是本体的价值）

1. **单位必须归一**：`mm/cm/m`、`MPa/bar`、`kW/HP` 统一到基准单位后再比较
2. **限值有方向**：`≥ / ≤ / 区间 / 等级枚举`，不能当字符串比
3. **条款有时效**：同一指标在不同版本标准里限值可能变严，必须按实施日期取现行版
4. **条款有引用链**：`见 5.2.3 条` 这种跳转要展开

## 5. 多跳链路（核心 Demo）

```
① 技术要求抽取
   招标规范书 表 3「主要技术参数」
   → Requirement{绝缘电阻, ≥100, MΩ}

② 条款匹配
   检索 → GB/T xxxx-20xx 第 5.2.3 条
   校验：该标准现行有效？被代替？
   → Clause{5.2.3, 绝缘电阻 ≥ 100 MΩ, 试验方法见 6.3}

③ 实测值获取
   检测报告 第 7 页 表 4
   → TestItem{绝缘电阻, 实测 250, MΩ, 方法 6.3}

④ 单位归一 + 比较 + 判定
   调工具 numeric_compare(250, "≥", 100, "MΩ")
   → Verdict{符合, 余量 150%}
   → Evidence{规范书 p.12 表3 / 标准 p.8 5.2.3 / 报告 p.7 表4}
```

**Demo 亮点**：故意放一个**不符合项**（例如实测 80 MΩ < 100 MΩ），
再看智能体能否给出「不符合 + 差异 + 建议整改方向 + 三处证据」。
比全对的 demo 可信得多。

## 6. MCP 工具 + Skill 拆分

### MCP 工具（自己写，体现工具开发能力）

| 工具 | 作用 | 为什么必须 |
|---|---|---|
| `standard_search` | 按参数名/关键词检索适用标准条款 | 跨标准库检索，非知识库单库 |
| `standard_status` | 查标准现行/废止/被代替 | 时效性判断，LLM 记不住 |
| `unit_convert` | 单位归一 | 避免模型自己换算出错 |
| `numeric_compare` | 按方向比较，返回余量与判定 | **核心**：判定不交给 LLM |
| `evidence_pack` | 组装证据链（文档/页/条款） | 统一溯源格式 |
| `report_export` | 导出核查报告 docx/pdf | 交付物 |

### Skill（可复用模板，体现沉淀）

| Skill | 输入 → 输出 | 复用性 |
|---|---|---|
| `extract_requirements` | 规范书 PDF → Requirement 列表 | 换任何品类都能用 |
| `match_clauses` | Requirement → Clause + 时效校验 | 同上 |
| `judge_compliance` | Requirement + TestItem → Verdict | 核心判定逻辑 |
| `generate_remediation` | 不符合项 → 整改建议 | 同上 |

**关键**：Skill 要参数化（品类、标准体系、单位制），并在答辩时演示
「同一套 Skill 换一个品类仍然工作」——这是赛题里「可复用、可快速部署」的直接证据。

## 7. 「低资源」叙事怎么写才可信

不要说「我们标注了 N 万条」，那跑偏了。要说闭环：

```
人工标注 50 条「条款—指标」三元组（种子）
   ↓ LLM 批量抽取候选
人工抽检 10%，错误回流成 few-shot 示例
   ↓ 重新抽取
本体覆盖率 62% → 85%，抽取准确率 71% → 89%
人工审核工时：每百条 4.2h → 1.1h
```

**三个数字必须真实测出来**（哪怕样本小），别编。评委一问细节就露。

## 8. 评测集设计

| 类型 | 题数 | 例子 |
|---|---|---|
| 单跳 | 10 | 某标准 5.2.3 条的限值是多少？ |
| 双跳 | 10 | 该参数在现行版标准里的限值，与规范书要求是否一致？ |
| 四跳全链 | 10 | 给定规范书+报告，逐条判定并给证据 |

**指标**：判定准确率、证据命中率（引用页/条款是否正确）、单位归一正确率

**基线对比**（必须有，否则说服力为零）：
- 基线 A：纯 LLM（直接贴文档问）
- 基线 B：纯 RAG（知识库问答，不调工具）
- 本方案：RAG + 工具编排

预期结论：单跳基线不差，**四跳全链差距拉开**——这就是方案价值的量化证明。

## 9. 三人分工（两周节奏）

| 角色 | 负责 | 第 1 周 | 第 2 周 |
|---|---|---|---|
| **A 平台/工具** | Nexent 部署、MCP server、Skill 编排 | 6 个 MCP 工具跑通 | Skill 封装 + 换品类验证 |
| **B 数据/本体** | 文档收集、解析、本体构建、标注 | 20 份文档 + schema 落地 + 50 条种子 | 半自动抽取闭环 + 指标测量 |
| **C 产品/叙事** | 评测集、demo 脚本、仓库、答辩 | 30 题评测集 + 基线跑分 | demo 打磨 + PPT + 开源整理 |

**第一周结束的验收点**：四跳链路能手工跑通一次（哪怕靠人肉拼），
第二周才有东西可自动化。

## 10. 风险清单

| 风险 | 概率 | 应对 |
|---|---|---|
| 标准全文拿不全 | 中 | 换团体标准/行业白皮书；或只用公开的推荐性国标 |
| 扫描件 OCR 质量差 | 高 | 用已配的 Qwen3-VL 走图片理解；先做 2 份验证再批量 |
| 本体设计过度复杂 | 高 | 只用 7 个实体，砍掉一切非必需属性 |
| 判定逻辑写死在提示词里 | 中 | **强制走工具**，这是评分点，不是偷懒的地方 |
| 品类扩太散 | 高 | 锁定 1 个品类做到穿，横向扩展留到最后 |

## 11. 立即可做的三件事（今天）

1. **锁定品类**：从「低压成套开关设备 / 工业离心泵 / 紧固件 / 电线电缆」里选一个
2. **下载 3 份文档**：1 份标准全文 + 1 份技术规范书 + 1 份检测报告
3. **建仓库**：GitCode 或 GitHub，README 三行也行，先占坑

> 开源是硬性要求，且**仓库结构从第一天就该按「别人能跑起来」的标准写**。
> 最后一周补 README 的队，基本都补不动。
