# 设备故障诊断五步流程

面向先进制造车间的设备运维智能体。把一次「设备报障」拆成五个可复用、可溯源的步骤，
保证每条结论都能落到具体的手册章节、具体的限值和具体的库存数量上。

## 何时使用

出现以下任一情形时加载本技能：

- 用户描述设备异常现象：异响、振动偏大、温升过高、漏油、压力不足、爬行、精度漂移、表面振纹
- 用户给出报警 / 故障代码：E-101 ~ E-108、H-201 ~ H-205
- 用户询问某个监测值是否超标（振动速度、径向跳动、温升、间隙、压力、力矩、油温）
- 报障后需要判断「换不换件」「备件够不够」「上次是怎么修的」

不适用：单纯的台账罗列（「有哪些设备」直接调 list_equipment 即可）、与设备无关的通用问答。

## 可用工具

| 工具 | 来源 | 用途 | 涉及步骤 |
|---|---|---|---|
| get_equipment | plant-structure (MCP) | 按编号 / 名称 / 型号 / 产线查设备详情，带出关联备件与适用故障代码 | 1 |
| get_fault_code | plant-structure (MCP) | 故障代码或现象名 → 标准处置 + 参考手册章节 | 2 |
| knowledge_base_search | 本地知识库 | 手册正文、历史工单、质检记录、BOM 原文 | 3、5 |
| get_threshold | plant-structure (MCP) | 报警线 / 停机线 / 允差 / 力矩的精确值 | 4 |
| get_spare_part | plant-structure (MCP) | 备件库存数量与单价 | 5 |
| list_equipment | plant-structure (MCP) | 在册设备清单 | 1（用户只给产线时） |
| ping | plant-structure (MCP) | 连通性自检 | 排查用 |

## 五步流程

### 第 1 步 · 定位设备

调用 get_equipment，keyword 传设备编号（CNC-01）、型号（VMC850）、名称或产线名。
必须拿到：设备编号、型号、所属产线、关键部件。

型号是后面所有查询的钥匙——限值跟着型号走，备件也跟着型号走。型号没定，不要往下走。
若用户只说了产线，先用 list_equipment 缩小到具体设备再进第 2 步。

### 第 2 步 · 归因分类

- 有报警代码：get_fault_code(code)，返回故障名称、可能原因、标准处置、参考手册章节。
- 只有现象：先 get_fault_code(现象名)；字典里查不到，再用 knowledge_base_search(现象) 找相似记载。

产出必须是一个明确的故障代码加一个手册章节号。这是多跳链路的第二跳，
第 3 步要拿这个章节号去手册正文里核对，不能只停在字典的结论上。

### 第 3 步 · 取手册正文

调用 knowledge_base_search，query 里必须带上设备型号或部件名加现象，
例如「VMC850 主轴异响 轴承预紧」。调用时**只传 query 一个参数**：
不要传 index_names（会检索落空），也不要传 top_k（接口不接受，传了直接报参数错误，
top_k 已在工具实例配置里固定为 5）。

产出：诊断步骤原文与处置措施，并记下出处《文件名》加章节号，
例如《maintenance_manual_cnc.txt》3.2.1。手册原文优先于自己的经验。

### 第 4 步 · 判定限值

调用 get_threshold(监测项) 取报警线与停机线，然后把现场实测值对到三档：

| 区间 | 判定 | 动作 |
|---|---|---|
| 低于报警线 | 正常 | 继续观察，按周期复测 |
| 报警线 ~ 停机线 | 报警 | 限期处理，加密监测，可先调参数 |
| 高于停机线 | 停机 | 立即停机检修，不得带病运行 |

限值表里没有的项，不要自己估算一个数。说「手册未给出该限值」，再给出可替代的判据。
不同类型设备（CNC / HYD / CLG / ELE）的限值不可互相套用。

### 第 5 步 · 备件与历史

- get_spare_part(名称或编号) 核库存与单价 → 判断够不够换、缺几个、换件成本多少。
- knowledge_base_search 查维修工单库里的同类记录 → 上次怎么处理、换了什么、花了多少工时。

两者合起来才能回答「现在该怎么办」：只查库存回答不了工期，只查工单回答不了当下的物料。

## 输出模板

固定三段，缺一不可：

1. **结论**——一句话给出判定：故障代码 + 严重程度（正常 / 报警 / 停机）+ 是否需要停机
2. **依据**——逐条列出，每条都带出处《文件名》加章节号；是数值就写明报警线与停机线，
   是库存就写明库存数与需求数
3. **建议动作**——按优先级排序；涉及换件的写明备件编号、规格与库存缺口

正文用中文自然语言。不要复述工具调用的参数，不要输出 JSON，不要出现代码块。

## 分支与例外

- **无故障代码、只有现象**：走第 2 步的现象分支，把最接近的代码标注为「疑似」，
  不要硬套成确定结论。
- **知识库与 MCP 都没有**：直接说「资料中未收录」，并列出已经查过哪些来源
  （4 个知识库中的哪几个、哪几个工具）。不要编造数值或型号。
- **库存不足**：写清缺口（需要 N / 库存 M / 缺 N-M），再给替代处置：降级运行、外部调件、
  或换用同一总成的替代型号。
- **同一现象对应多个候选故障**：按手册给出的可能性排序，列出鉴别性检查项，
  不要只给一个结论就收尾。
- **用户只想问限值**：第 1 步加第 4 步即可，不必强行走完五步。
- **跨设备类别**：VMC 与 HMC 的主轴轴承型号不同（SP-1001 与 SP-1002），
  HPU-40 与 HPU-63 的备件也不通用。

## 常见错误

| 错误 | 后果 | 纠正 |
|---|---|---|
| 用知识库模糊召回代替精确查询 | 型号、库存、限值张冠李戴 | 编号与数值一律走 MCP 工具 |
| 调用 knowledge_base_search 时传 index_names 或 top_k | 检索落空 / 直接报参数错误 | 只传 query 一个参数 |
| 把 VMC 的轴承装到 HMC 上 | 选型错误，件装不上 | 先定型号再选备件 |
| 回答里省略出处 | 不可溯源，现场无法复核 | 每条结论后加《文件名》加章节号 |
| 把报警线当停机线 | 该停机的被判成继续观察 | 明确区分报警线与停机线 |
| 凭经验补一个「通常值」 | 编造数据，评审一票否决 | 没有就说资料中未收录 |
